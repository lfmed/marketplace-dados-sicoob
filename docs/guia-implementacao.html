O código do app e do banco é entregue pronto, idempotente e parametrizado — nenhum ID fica fixo fora de app/config.py. O trabalho do cliente é provisionar a infraestrutura e apontar o app para a governança e os schemas reais. Todos os comandos abaixo são reproduzíveis em qualquer workspace.

◇

Arquitetura em produção

3 schemas (catálogo plataforma): governanca + gestao_acesso (mirrors do Motor) e marketplace_app (workflow do app).

O app não é a fonte da verdade — ele consome o que os Motores do cliente mantêm em Delta (catálogo plataforma): governanca (taxonomia + tabela_aisn) e gestao_acesso (referência de acesso: ativos, grupos, owners, hierarquia). Esses dois são replicados para o Lakebase por synced tables (somente leitura). O catálogo gira em torno do ativo (em gestao_acesso) — a unidade liberável em qualquer nível. O app grava só o seu workflow no schema marketplace_app e, na efetivação, inclui o beneficiário no grupo do ativo — que já detém o GRANT no Unity Catalog (concedido pelo Motor) — agindo como um Service Principal. Catálogo e schemas são parametrizáveis (env).

  1. Os Motores (Governança + Acesso) do cliente mantêm, em Delta no catálogo plataforma: governanca (taxonomia + tabela_aisn, único com o alvo UC) e gestao_acesso (referência de acesso: ativos com o grupo embutido, grupos, owners, hierarquia).
  2. Synced tables replicam esses dois schemas Delta para o Lakebase (governanca + gestao_acesso, mirrors de leitura). O app grava só o seu workflow no schema marketplace_app.
  3. O usuário entra via SSO, navega o catálogo de ativos e pede acesso; o app registra cada solicitação/autorização/aprovação em marketplace_app.
  4. Na aprovação final do owner do ativo, o worker inclui o beneficiário no grupo do ativo (via SCIM). O grupo (de conta) já detém o GRANT no Unity Catalog, concedido pelo Motor — o app só faz a associação. Revogar = remover o membro. O app age como o Service Principal.
  5. O beneficiário (usuário nominal ou um grupo do qual é membro) passa a ter acesso por ser membro do grupo do ativo, de forma auditável (RF-081..088).

Obter o código (Git → Databricks)

De onde vem o código e como levá-lo para a workspace.

O código-fonte do app está em um repositório Git. Há duas formas de trazê-lo para a workspace: via Git folders do próprio Databricks (recomendado — clona o repo dentro da workspace e atualiza com um pull) ou clonando localmente e usando databricks sync (passo 5).

repositório do projeto
https://github.com/lfmed/marketplace-dados-sicoob

Opção A — Git folders no Databricks (recomendado)

Como o repositório é privado, primeiro configure as credenciais Git na workspace em Settings → Linked accounts (usuário do GitHub + token/PAT com acesso de leitura). Depois clone o repo para dentro da workspace:

bash
# Via UI: Workspace → Repos → Add repo → cole a URL do repositório

# Ou via CLI:
databricks repos create https://github.com/lfmed/marketplace-dados-sicoob.git gitHub \
  --path /Workspace/Users/<voce>/marketplace-dados

# atualizar depois, ao chegarem novos commits:
databricks repos update /Workspace/Users/<voce>/marketplace-dados --branch main

Com o código já na workspace, o --source-code-path do deploy (passo 5) aponta direto para essa pasta — não é preciso o databricks sync.

Opção B — Clonar localmente + sync

Se preferir trabalhar da sua máquina, clone o repo e use o databricks sync do passo 5 para enviar o código à workspace.

bash
git clone https://github.com/lfmed/marketplace-dados-sicoob.git
cd marketplace-dados-sicoob
pip install -r requirements.txt
# ...siga para os passos 1–5
privado

Repositório privado. Solicite acesso de leitura ao responsável (ou use o token/PAT fornecido). Nenhum segredo vive no código — credenciais e IDs de recurso ficam em variáveis de ambiente / secret da app (passo 2).

Pré-requisitos

Projeto Lakebase disponível · CLI opcional (firewall? use a rota sem CLI).

sem CLI

Firewall bloqueia a CLI databricks? Não precisa dela. Com o repositório já clonado no Databricks (Git folders, passo anterior), crie e publique o app pela UI de Apps apontando para a pasta do repo (passo 5). Na subida, a própria app cria o schema marketplace_app no Lakebase (agindo como o service principal, server-side) e loga cada ponto provisionado em App ▸ Logs. Os comandos de CLI abaixo são só uma alternativa para quem a tiver. As synced tables dos mirrors (governança/acesso) continuam sendo responsabilidade do Motor do cliente.

O único recurso que precisa existir antes de tudo é o projeto Lakebase — o banco Postgres autoscaling do app, que escala a compute conforme a carga e chega a zero quando ocioso (sem custo de servidor parado). Se você tiver o Databricks CLI (rota alternativa), ele autentica por OAuth e provisiona/publica pela linha de comando; caso contrário, tudo é feito pela UI e pelo boot do app. O SQL Warehouse serverless (item 2 do checklist) precisa estar ativo — executa os GRANT/REVOKE e, se usar synced tables nativas, o registro delas.

bash
# 1. Autentica o CLI na workspace de produção do cliente (abre o browser p/ OAuth)
databricks auth login --host https://<workspace>.cloud.databricks.com

# 2. Cria o projeto Lakebase (autoscaling, PG 17) — pule se já existir
databricks postgres create-project marketplace-dados \
  --json '{"spec":{"display_name":"Marketplace Dados Sicoob","pg_version":"17"}}'

A criação do projeto é uma operação de longa duração: o comando retorna quando o projeto, a branch production e o endpoint primary estão prontos. Confirme com databricks postgres list-projects. O SQL Warehouse serverless (item 2 do checklist) também precisa estar ativo — é ele que executa o DDL do banco e os comandos GRANT/REVOKE.

requer

Pré-condições. Para registrar as synced tables nativas dos mirrors (plataforma.governanca + plataforma.gestao_acesso), quem roda o setup precisa de CREATE CATALOG no metastore. E para efetivar, o Service Principal do app precisa ser gerente dos account groups dos ativos (para incluir/remover membros) — não precisa de MANAGE nos schemas de dados, pois o grant do grupo já é concedido pelo Motor (PROVISION_GROUP_GRANT=false).

Configuração

Parâmetros por ambiente — via app.yaml ou variáveis de ambiente.

Todo o comportamento específico da workspace é controlado por variáveis de ambiente, lidas de forma central em app/config.py — nenhum ID de recurso fica embutido no código. Isso é o que torna a mesma base portável de dev para o cliente: só mudam os valores abaixo. Em produção, prefira valueFrom no app.yaml (que resolve o ID a partir de um recurso vinculado à app) em vez de value com o ID escrito à mão, e configure a chave de sessão como um secret, nunca em texto puro.

Catálogo e schemas são parametrizáveis (GOV_CATALOG, SCHEMA_*) — lidos em app/config.py/app/schemas.py e injetados em todas as queries, então a mesma base roda no dev (catálogo fixo) e no cliente (plataforma) só mudando env. Em produção, GROUPS_SCOPE=account (a concessão usa grupos de conta — principais válidos no UC) exige DATABRICKS_ACCOUNT_ID e o SP do app como gerente desses grupos; e PROVISION_GROUP_GRANT=false mantém o app só na associação (o Motor já concedeu o grant do grupo).

Banco de dados

Um único entrypoint idempotente provisiona tudo.

O banco do app tem 3 schemas no Lakebase. governanca e gestao_acesso são mirrors de leitura — populados por synced tables a partir do Delta do Motor (plataforma.*); o app nunca escreve neles. marketplace_app é o schema transacional do app — solicitações, autorizações, aprovações, acessos, execuções técnicas e trilha de auditoria. Como a governança já existe, em produção o comando não semeia nada: só cria o marketplace_app e registra as synced tables.

sem CLI · no boot

Deploy sem CLI: o schema marketplace_app é criado pela própria app na subida. Controlado por AUTO_BOOTSTRAP_APP_SCHEMA (default true), o app conecta no Lakebase pelo service principal, aplica o DDL (idempotente, com advisory lock entre workers) e loga cada tabela criada e cada mirror verificado em App ▸ Logs — ex.: ✓ schema 'marketplace_app' pronto: 7 tabelas, ✓ gestao_acesso.ativo_aisn: 74 linhas. Alternativas sem CLI: rodar from app.bootstrap import run; run() num notebook do repo clonado, ou colar db/ddl/marketplace_app.sql no editor SQL do Lakebase. E as synced tables dos mirrors (governanca/gestao_acesso) também são registráveis sem CLI: rode o notebook notebooks/registrar_synced_tables.py no workspace (server-side — chama db.native_sync_setup; exige CREATE CATALOG). O db.setup abaixo é para quem tem CLI e quer fazer tudo num comando.

bash
# PRODUÇÃO — cria marketplace_app + registra synced tables dos mirrors, SEM seed
python -m db.setup --mode native --no-seed

# DEV / demo — sync controlado + seed sintético (catálogo fixo do dev)
python -m db.setup --mode dev

Em --mode native (produção), o Lakebase mantém synced tables nativas que replicam plataforma.governanca e plataforma.gestao_acesso — por isso exige CREATE CATALOG no metastore. O schema marketplace_app (workflow) é criado nativo e é o único gravável. Em --mode dev, um sync controlado copia um schema Delta sintético (catálogo do dev). O --seed liga por padrão em dev e desliga em native.

Dois caminhos: automatizado ou manual

A criação das tabelas e o seed são decisões independentes. Você pode deixar o db.setup fazer tudo, aplicar os DDLs à mão, e popular a governança com o seu próprio processo — em qualquer combinação.

bash · criação das tabelas
# A) Automatizado — cria schemas/tabelas, registra o catálogo e as synced tables
python -m db.setup --mode native --no-seed

# B) Manual — aplica os DDLs direto no Lakebase (ex.: via psql)
#    o token do Lakebase é OAuth e expira em 1h — gere sob demanda
psql "$LAKEBASE_URL" -f db/ddl/02_gestao_acesso.sql   # tabelas do app (sempre)
psql "$LAKEBASE_URL" -f db/ddl/01_governanca.sql      # opcional: governança no Lakebase
bash · seed (opcional)
# O seed é OPCIONAL e independente da criação das tabelas:
python -m db.setup --mode dev              # dados sintéticos (demo)
python -m db.setup --mode native --no-seed # sem seed — governança vem do Motor
# ...ou popule a governança com o seu próprio ETL / manualmente
catálogos

Quais catálogos? GOV_CATALOG (ex.: plataforma) é o catálogo Delta do Motor, com os schemas governanca e gestao_acesso — o cliente o cria/possui (já existe). LAKEBASE_UC_CATALOG (ex.: lakebase_marketplace) registra o Postgres do Lakebase no UC e recebe as synced tables (mirror somente-leitura dos dois schemas); é criado por db/native_sync_setup.py se o executor tiver CREATE CATALOG, ou um admin do metastore o pré-cria. UC_CATALOG só importa no dev (dados sintéticos mkt_*); em produção os catálogos dos dados vêm de tabela_aisn.

yaml · env dos catálogos
GOV_CATALOG:         "plataforma"                 # catálogo Delta do Motor (governanca + gestao_acesso)
LAKEBASE_UC_CATALOG: "lakebase_marketplace"       # registra o Postgres no UC (synced tables)
# UC_CATALOG só no dev (dados sintéticos mkt_*)

Permissões do app (service principal)

O app efetiva o acesso agindo como o SP — que precisa poder conceder.

Quando roda no Databricks Apps, o app tem a identidade de um service principal (SP). Como a concessão é por associação a grupo e o Motor já concedeu o grant do grupo (PROVISION_GROUP_GRANT=false), em produção o SP faz uma coisa na efetivação: incluir/remover o beneficiário no grupo do ativo — por isso precisa ser gerente dos account groups (ou admin de conta). Não precisa de MANAGE nos schemas de dados. Além disso: role no Lakebase (OAuth), CAN_USE no warehouse e SELECT nas tabelas Delta de origem (para as synced tables).

console de conta / SCIM
# Torne o SP do app GERENTE de cada account group de ativo (nome_grupo_ativo).
# Via console: Conta ▸ Grupos ▸ <grupo do ativo> ▸ Permissões ▸ adicionar o SP como "Manager".
# (Ou via API de conta / rule sets — role: roles/group.manager.)
bash · warehouse + role Lakebase + SELECT nos Delta
# Warehouse: CAN_USE para o SP
databricks warehouses set-permissions <wh> --json '{"access_control_list":[
  {"service_principal_name":"<sp-client-id>","permission_level":"CAN_USE"}]}'

# Lakebase: cria um role Postgres para o SP
databricks postgres create-role projects/marketplace-dados/branches/production \
  --role-id app-marketplace \
  --json '{"spec":{"identity_type":"SERVICE_PRINCIPAL",
                   "auth_method":"LAKEBASE_OAUTH_V1",
                   "postgres_role":"<sp-client-id>"}}'
sql · UC (SELECT nos Delta de origem) + Postgres (marketplace_app)
-- UC: o SP lê os Delta que alimentam as synced tables
GRANT USE CATALOG ON CATALOG plataforma TO `<app-sp-client-id>`;
GRANT USE SCHEMA, SELECT ON SCHEMA plataforma.governanca TO `<app-sp-client-id>`;
GRANT USE SCHEMA, SELECT ON SCHEMA plataforma.gestao_acesso TO `<app-sp-client-id>`;

-- Postgres: só o workflow (marketplace_app) é gravável; os mirrors são leitura
GRANT CONNECT ON DATABASE databricks_postgres TO "<sp-client-id>";
GRANT USAGE ON SCHEMA marketplace_app TO "<sp-client-id>";
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA marketplace_app TO "<sp-client-id>";
ALTER DEFAULT PRIVILEGES IN SCHEMA marketplace_app
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO "<sp-client-id>";

Cada frente cobre um trecho: ser gerente dos account groups é o que permite a associação (a concessão); o role no Lakebase dá o token OAuth para o Postgres; o SELECT nos Delta alimenta as synced tables; e no Postgres o SP lê os mirrors e lê/grava o workflow em marketplace_app.

grupos

A concessão é por associação ao grupo do ativo (não GRANT por usuário). Em produção esses grupos são account groups (GROUPS_SCOPE=account) — principais válidos no UC — e o SP precisa ser gerente deles para incluir/remover membros (ou admin de conta). Em dev sem conta (workspace), a associação funciona mas o grant do grupo não propaga no UC (grupo workspace-local não é principal — D-009); lá o SP precisa poder gerenciar grupos do workspace (ex.: estar em admins).

Publicar o app

Databricks Apps — criar, sincronizar, publicar.

Com o código já disponível (ver Obter o código): se você usou Git folders, pule o sync e aponte o --source-code-path para a pasta do repo na workspace; se clonou localmente, use o sync para enviar o código.

bash
databricks apps create marketplace-dados

databricks sync . /Workspace/Users/<voce>/marketplace-dados

databricks apps deploy marketplace-dados \
  --source-code-path /Workspace/Users/<voce>/marketplace-dados

São três comandos com papéis distintos: apps create registra a aplicação (uma vez só, e é aqui que o service principal do app é criado); sync envia o código para uma pasta no Workspace; e apps deploy publica aquele código como a versão ativa. Para atualizações depois, basta repetir sync + deploy — não é preciso recriar a app.

O comando de runtime é gunicorn -c gunicorn.conf.py app:app, definido no app.yaml — Flask em produção roda sob Gunicorn, não no servidor de desenvolvimento. O app faz bind na porta da variável DATABRICKS_APP_PORT (nunca 8080). Configure FLASK_SECRET_KEY como secret/recurso da app, e vincule os recursos (warehouse, Lakebase) para que o valueFrom do app.yaml resolva os IDs.

Verificação

Prove o fluxo ponta a ponta com um grant real.

bash
curl -s https://<app-url>/health          # -> {"status":"ok"}

# Suite de integração apontando para a workspace
pytest tests/

O endpoint /health confirma que o app subiu e conecta no banco. A suíte de integração exercita as regras/o modelo e dois fluxos ponta a ponta (associação real ao grupo do ativo). Depois, faça o teste que mais convence: percorra o fluxo no próprio app — solicitar → autorizar (gestor) → aprovar (owner do ativo) → efetivar. A efetivação inclui o beneficiário no grupo do ativo; confirme os dois lados — o grupo detém o grant no objeto, e o beneficiário é membro do grupo:

sql
-- o GRUPO do ativo detém SELECT no objeto (schema ou tabela, por nível)
SHOW GRANTS ON SCHEMA <UC_CATALOG>.<schema_real>;
-- e o beneficiário é membro do grupo do ativo (via console/Account SCIM)
esperado

Após a efetivação, o grupo do ativo aparece com SELECT (e USE SCHEMA) no objeto e o beneficiário passa a ser membro desse grupo — logo tem acesso. Após a revogação pelo owner, o beneficiário sai do grupo. Todo o ciclo é registrado na trilha de auditoria (RF-081..088). Em dev sem account groups, o grant do grupo não propaga; valida-se a associação.
