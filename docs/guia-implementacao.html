O código do app e do banco é entregue pronto, idempotente e parametrizado — nenhum ID fica fixo fora de app/config.py. O trabalho do cliente é provisionar a infraestrutura e apontar o app para a governança e os schemas reais. Todos os comandos abaixo são reproduzíveis em qualquer workspace.

◇

Arquitetura em produção

Três planos: a governança (origem, no cliente), o estado (Lakebase) e a efetivação (Unity Catalog).

O app não é a fonte da verdade da governança — ele a consome. Os metadados (domínios, iniciativas, camadas, owners, hierarquia) são mantidos pelo Motor de Governança do cliente em tabelas Delta e replicados para o Lakebase por synced tables. O app lê essa governança, registra o ciclo de vida das solicitações no schema gestao_acesso e, na efetivação, executa GRANT/REVOKE reais nos schemas de dados do Unity Catalog — agindo como um Service Principal.

  1. Motor de Governança mantém os metadados (domínios, iniciativas, camadas, owners, hierarquia) em tabelas Delta no Unity Catalog — fonte da verdade, fora do app.
  2. Synced tables replicam essas tabelas Delta para o schema governanca no Lakebase (espelho de leitura, atualizado continuamente).
  3. O usuário entra via SSO; o app lê a governança do Lakebase e registra cada solicitação, autorização e aprovação no schema transacional gestao_acesso.
  4. Na aprovação final do owner, o worker de efetivação executa GRANT/REVOKE no schema real do Unity Catalog — agindo como o Service Principal do app.
  5. O beneficiário (usuário nominal, grupo exploratório ou service principal) passa a ter acesso ao schema, de forma auditável (RF-081..088).

Pré-requisitos

CLI autenticado e o projeto Lakebase disponível.

Duas coisas precisam existir antes de qualquer outra: o Databricks CLI autenticado na workspace de produção e um projeto Lakebase. O CLI é a ferramenta que provisiona o banco, concede as permissões e publica o app; a autenticação usa OAuth e fica salva no perfil local. O projeto Lakebase é o banco Postgres autoscaling do app — ele escala a compute conforme a carga e pode chegar a zero quando ocioso, então não há custo de servidor parado.

bash
# 1. Autentica o CLI na workspace de produção do cliente (abre o browser p/ OAuth)
databricks auth login --host https://<workspace>.cloud.databricks.com

# 2. Cria o projeto Lakebase (autoscaling, PG 17) — pule se já existir
databricks postgres create-project marketplace-dados \
  --json '{"spec":{"display_name":"Marketplace Dados Sicoob","pg_version":"17"}}'

A criação do projeto é uma operação de longa duração: o comando retorna quando o projeto, a branch production e o endpoint primary estão prontos. Confirme com databricks postgres list-projects. O SQL Warehouse serverless (item 2 do checklist) também precisa estar ativo — é ele que executa o DDL do banco e os comandos GRANT/REVOKE.

requer

Dois privilégios são pré-condição. Para as synced tables nativas (modo native, passo 3), quem roda o setup precisa de CREATE CATALOG no metastore — é o que permite ao Lakebase materializar o espelho da governança. E para conceder/revogar acessos, o Service Principal do app precisa de USE CATALOG + MANAGE nos schemas alvo (configurado no passo 4). Sem eles, o setup e a efetivação falham com erro de permissão.

Configuração

Parâmetros por ambiente — via app.yaml ou variáveis de ambiente.

Todo o comportamento específico da workspace é controlado por variáveis de ambiente, lidas de forma central em app/config.py — nenhum ID de recurso fica embutido no código. Isso é o que torna a mesma base portável de dev para o cliente: só mudam os valores abaixo. Em produção, prefira valueFrom no app.yaml (que resolve o ID a partir de um recurso vinculado à app) em vez de value com o ID escrito à mão, e configure a chave de sessão como um secret, nunca em texto puro.

UC_CATALOG
Catálogo UC onde estão os schemas dos dados. Ex.: catalogo_producao
DATABRICKS_WAREHOUSE_ID
Warehouse para DDL/GRANT/REVOKE.
LAKEBASE_ENDPOINT
projects/marketplace-dados/branches/production/endpoints/primary
GRANT_EXECUTE_REAL
Executa GRANT/REVOKE reais no UC. true
APP_ENABLE_PROXY
Seletor "atuar como" (demo). Produção: false
yaml · app.yaml
command: ["gunicorn", "-c", "gunicorn.conf.py", "app:app"]
env:
  - name: UC_CATALOG
    value: "<catalogo_uc_do_cliente>"
  - name: DATABRICKS_WAREHOUSE_ID
    value: "<warehouse_id>"
  - name: LAKEBASE_ENDPOINT
    value: "projects/marketplace-dados/branches/production/endpoints/primary"
  - name: GRANT_EXECUTE_REAL
    value: "true"
  - name: APP_ENABLE_PROXY
    value: "false"        # produção: sem "atuar como"

Duas variáveis merecem atenção em produção. GRANT_EXECUTE_REAL=true liga a efetivação real no Unity Catalog — com false, o app registra todo o fluxo mas não executa o grant (útil só para ensaios). E APP_ENABLE_PROXY=false desativa o seletor "atuar como" (usado na demo para simular personas); em produção a identidade vem exclusivamente do SSO, pelo cabeçalho X-Forwarded-Email que o Databricks Apps injeta a cada requisição.

Banco de dados

Um único entrypoint idempotente provisiona tudo.

O banco do app tem dois schemas no Lakebase, com papéis distintos. governanca é um espelho de leitura — populado a partir das tabelas Delta do Motor de Governança via synced tables; o app nunca escreve nele. gestao_acesso é o schema transacional do app — é onde ficam solicitações, autorizações, aprovações, acessos, execuções técnicas e a trilha de auditoria. O comando abaixo cria e popula os dois de forma idempotente (pode rodar de novo com segurança).

bash
# PRODUÇÃO — synced tables nativas, SEM seed sintético
python -m db.setup --mode native --no-seed

# DEV / demo — sync controlado Delta→Lakebase + seed sintético
python -m db.setup --mode dev

A diferença entre os modos é como a governança chega ao Lakebase. Em --mode native (produção), o Lakebase mantém synced tables nativas que replicam continuamente o Delta real do Motor — por isso exige CREATE CATALOG no metastore. Em --mode dev, um sync controlado copia um schema Delta sintético, sem exigir esse privilégio. Já o --seed controla se dados sintéticos são criados: ele liga por padrão em dev e desliga em native, e você pode forçar qualquer combinação (--seed / --no-seed).

O que cada passo faz

PassoAçãoProdução (--no-seed)
1Cria schemas Lakebase (gestao_acesso; governanca só em dev).Sempre
2Cria governança sintética em Delta + seed.Pulado
3Cria alvos de GRANT sintéticos (grupos + schemas mkt_*).Pulado
4Popula governanca no Lakebase (synced tables nativas a partir do Delta do Motor).Sempre
--seed / --no-seed

O seed é opcional. Liga por padrão em --mode dev e desliga em --mode native. Aponte as synced tables (db/native_sync_setup.py) para as tabelas Delta reais mantidas pelo Motor de Governança, no lugar do schema sintético marketplace_governanca.

Permissões do app (service principal)

O app efetiva o acesso agindo como o SP — que precisa poder conceder.

Quando roda no Databricks Apps, o app tem a identidade de um service principal (SP). É esse SP que executa os grants — então ele precisa ter poder para conceder. São três frentes de permissão, cada uma por um motivo específico. O script scripts/grant_app_sp.py <sp_client_id> aplica o lado Unity Catalog e o warehouse automaticamente; abaixo estão os comandos equivalentes explícitos, para auditoria.

Por que MANAGE no catálogo? Para conceder USE CATALOG a um beneficiário, o próprio SP precisa poder administrar esse privilégio no catálogo — daí MANAGE ON CATALOG. Nos schemas alvo, MANAGE permite ao SP conceder e revogar SELECT/MODIFY em nome dos owners.

sql · Unity Catalog
-- MANAGE no catálogo é necessário para o SP conceder USE CATALOG aos beneficiários
GRANT USE CATALOG, MANAGE ON CATALOG <UC_CATALOG> TO `<app-sp-client-id>`;
GRANT USE SCHEMA, MANAGE ON SCHEMA <UC_CATALOG>.<schema_real> TO `<app-sp-client-id>`;
bash · warehouse + role Lakebase
# Warehouse: CAN_USE para o SP
databricks warehouses set-permissions <wh> --json '{"access_control_list":[
  {"service_principal_name":"<sp-client-id>","permission_level":"CAN_USE"}]}'

# Lakebase: cria um role Postgres para o SP
databricks postgres create-role projects/marketplace-dados/branches/production \
  --role-id app-marketplace \
  --json '{"spec":{"identity_type":"SERVICE_PRINCIPAL",
                   "auth_method":"LAKEBASE_OAUTH_V1",
                   "postgres_role":"<sp-client-id>"}}'
sql · Postgres (como owner do projeto)
GRANT CONNECT ON DATABASE databricks_postgres TO "<sp-client-id>";
GRANT USAGE ON SCHEMA governanca TO "<sp-client-id>";
GRANT SELECT ON ALL TABLES IN SCHEMA governanca TO "<sp-client-id>";
GRANT USAGE ON SCHEMA gestao_acesso TO "<sp-client-id>";
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA gestao_acesso TO "<sp-client-id>";
ALTER DEFAULT PRIVILEGES IN SCHEMA gestao_acesso
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO "<sp-client-id>";

Cada frente cobre um trecho do fluxo: o warehouse (CAN_USE) é onde o SP executa o SQL de grant; o role no Lakebase dá ao SP um token OAuth para conectar no Postgres; e os grants no Postgres deixam o SP ler a governança (só SELECT) e ler e escrever o ciclo de vida em gestao_acesso. O ALTER DEFAULT PRIVILEGES garante que tabelas criadas no futuro já nasçam acessíveis ao SP.

grupos

Grants a grupo exigem account groups no Unity Catalog (D-009). Grupos criados via SCIM que são workspace-local resultam em ERRO_EFETIVACAO (tratável/reprocessável). Em produção, use grupos de conta reais.

Publicar o app

Databricks Apps — criar, sincronizar, publicar.

bash
databricks apps create marketplace-dados

databricks sync . /Workspace/Users/<voce>/marketplace-dados

databricks apps deploy marketplace-dados \
  --source-code-path /Workspace/Users/<voce>/marketplace-dados

São três comandos com papéis distintos: apps create registra a aplicação (uma vez só, e é aqui que o service principal do app é criado); sync envia o código para uma pasta no Workspace; e apps deploy publica aquele código como a versão ativa. Para atualizações depois, basta repetir sync + deploy — não é preciso recriar a app.

O comando de runtime é gunicorn -c gunicorn.conf.py app:app, definido no app.yaml — Flask em produção roda sob Gunicorn, não no servidor de desenvolvimento. O app faz bind na porta da variável DATABRICKS_APP_PORT (nunca 8080). Configure FLASK_SECRET_KEY como secret/recurso da app, e vincule os recursos (warehouse, Lakebase) para que o valueFrom do app.yaml resolva os IDs.

Verificação

Prove o fluxo ponta a ponta com um grant real.

bash
curl -s https://<app-url>/health          # -> {"status":"ok"}

# Suite de integração apontando para a workspace
pytest tests/

O endpoint /health confirma que o app subiu e conecta no banco. A suíte de integração exercita as regras de negócio e um fluxo ponta a ponta com grant/revoke reais. Depois, faça o teste que mais convence: percorra o fluxo no próprio app — solicitar → autorizar (gestor) → aprovar (owner) → efetivar — e confirme a concessão no Catalog Explorer ou por SQL, antes e depois:

sql
SHOW GRANTS ON SCHEMA <UC_CATALOG>.<schema_real>;
esperado

Após a efetivação, o beneficiário aparece com SELECT (e USE SCHEMA) no schema; após a revogação pelo owner, a linha some. Todo o ciclo é registrado na trilha de auditoria do app (RF-081..088).
